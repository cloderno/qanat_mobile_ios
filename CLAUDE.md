# Qanat для iOS

Порт Android-приложения из `D:\qanat_mobile_android` на SwiftUI. Поведение, строки и API — как в Android-версии:
при правках сверяйся с ней (тот же экран/класс обычно называется так же). Проект Xcode генерируется XcodeGen из
`project.yml` — `.xcodeproj` в git не хранится. Сборка — только на Mac (см. README.md).

Если следующий шаг не требует моего участия, продолжай. Сообщай о ходе работы в том же сообщении, в котором указываешь следующее действие.

Остановись и спроси меня, только если без моего ответа нельзя продолжить, либо перед рискованными действиями: удалением данных, принудительной отправкой изменений, изменением публичного API или правками за пределами этого репозитория.

## Связь с бэкенд-агентом Qanat

Сервер (API, база, голосовой сервер, push) делает другой агент Claude на этом же
аккаунте. Связь через SendMessage (список сессий — ListAgents).

- Адресат — это `from` из ПОСЛЕДНЕГО входящего `cross-session-message` от бэкенда,
  а не фиксированное имя сессии: имя сессии может совпадать со старыми offline-копиями
  («Технический аудит Qanat» — таких несколько, часть из них старые). Если сам бэкенд
  в сообщении прямо называет адрес для ответа — используй его.
- Нужно что-то от сервера (новый эндпоинт, поле, ошибка API, непонятный ответ) —
  пиши ему: что нужно, для какого экрана, пример запроса и ожидаемого ответа.
  Не придумывай формат API сам и не обходи сервер.
- Он присылает тебе задания по приложению (что изменилось в API, что поддержать) —
  делай их и отвечай коротко: что сделал, коммит, что осталось.
- Источник правды по API — https://qm.e-vko.kz/api/v1/mobile/docs (обновляется
  вместе с сервером). Все эндпоинты приложения — в /api/v1/mobile/.
- Пиши по-русски, одно сообщение — одна тема.

Канал работает, пока обе сессии открыты и подключены. Если сообщение не доходит (адресат offline), сообщи об этом пользователю.

## Архитектура

Проект организуй по принципу **Feature-Based + Clean Architecture**.

Каждая feature должна быть максимально изолирована и разделена на слои:

* **presentation** — UI, ViewModel, UI state/event/effect;
* **domain** — бизнес-логика, модели предметной области, Repository interfaces, UseCases;
* **data** — реализации Repository, API, database, DTO, Entity, mappers и источники данных.

Зависимости направляй внутрь:

**presentation → domain ← data**

Domain не должен зависеть от UIKit, SwiftUI, URLSession, Meta Wearables SDK, Firebase и других деталей реализации.

Общие компоненты выноси в `core` только тогда, когда они действительно используются несколькими features. Не создавай `core` ради предполагаемого будущего переиспользования.

Структуру проекта предпочитай feature-based, например:

```text
Qanat/
    App/                 — точка входа, AppContainer (DI), AppRoot (навигация), push
    Feature/
        Auth/
            Presentation/
            Domain/
            Data/
        Chat/ Voice/ Glasses/ Settings/ Profile/
    Core/
        Network/ Storage/ Push/ Audio/ Glasses/ Common/ DesignSystem/
```

Не создавай отдельные Swift-пакеты или таргеты для каждой папки, если текущему проекту это не требуется.

## Принципы разработки

Следуй им в каждой правке кода:

1. **SOLID** — применяй качественное объектно-ориентированное проектирование, но без создания лишних абстракций.

2. **DRY** — не повторяйся: прежде чем писать новый код, найди существующую реализацию в репозитории и переиспользуй её. Повторяющуюся логику выноси в одно место только тогда, когда это действительно уменьшает сложность.

3. **KISS** — делай проще: из нескольких рабочих решений выбирай самое простое, понятное и соответствующее текущей архитектуре проекта.

4. **YAGNI** — не создавай то, что пока не нужно. Не добавляй заранее UseCase, Repository, интерфейсы, abstraction layer, generic-компоненты, настройки или extension-функции только «на будущее».

5. **SRP** — каждый класс, функция и компонент должны иметь одну понятную ответственность. ViewModel не должна превращаться в место для сетевых запросов, работы с БД и бизнес-логики.

6. **Open/Closed** — расширяй существующее поведение, не ломая работающий код. Новую функциональность по возможности добавляй как отдельную feature или компонент, не переписывая несвязанный существующий код.

7. **Dependency Inversion** — domain не должен зависеть от data и Android Framework. Repository protocols находятся в domain, а их реализации — в data. Зависимости передавай через инициализаторы; связывает их корень композиции `App/AppContainer.swift`.

8. **Composition over Inheritance** — предпочитай композицию и небольшие компоненты глубоким иерархиям наследования.

9. **Separation of Concerns** — разделяй ответственность:

   * UI отвечает за отображение и пользовательские действия;
   * ViewModel управляет состоянием presentation;
   * UseCase содержит конкретную бизнес-операцию;
   * Repository предоставляет данные domain-слою;
   * data отвечает за API, БД, кеш и преобразование данных;
   * DI отвечает за создание и связывание зависимостей.

10. **Unidirectional Data Flow** — состояние движется от ViewModel к UI, действия пользователя — от UI к ViewModel. Не изменяй состояние UI напрямую из Repository, UseCase или DataSource.

11. **Single Source of Truth** — для каждого состояния должен существовать один источник истины. Не дублируй одно и то же состояние одновременно в нескольких слоях без необходимости.

12. **Fail Fast** — проверяй некорректные входные данные на границах системы. Не скрывай ошибки пустыми `catch`, `nil` или значениями по умолчанию, если это маскирует проблему. Ошибки должны быть понятными и обрабатываться на подходящем слое.

13. **State over scattered flags** — вместо набора независимых `isLoading`, `isError`, `data` и подобных флагов предпочитай единое понятное состояние экрана, если это делает состояние однозначным и исключает невозможные комбинации.

14. **Immutability** — предпочитай неизменяемые модели и состояния. UI state должен обновляться созданием нового состояния, а не неконтролируемой мутацией существующего.

15. **Measure First** — не оптимизируй код без необходимости. Сначала измерь проблему с помощью логов, Instruments или других подходящих инструментов, затем оптимизируй.

16. **Lifecycle awareness** — учитывай жизненный цикл iOS (scenePhase, фон, аудиосессия). Не допускай циклов сильных ссылок: в долгоживущих замыканиях и Task — `[weak self]`.

17. **Single responsibility for ViewModel** — ViewModel не должна становиться «бог-объектом». Если логика относится к domain, вынеси её в UseCase; если относится к data — в Repository/DataSource.

18. **Repository abstraction** — UI и domain не должны знать, откуда пришли данные: API, Keychain, кеш или другой источник. Выбор источника и синхронизация должны находиться в data-слое.

19. **Mapping at boundaries** — не передавай DTO или другие data-модели непосредственно в presentation/domain, если это связывает слои. Преобразуй модели на границе соответствующего слоя.

20. **Feature isolation** — одна feature не должна напрямую обращаться к внутренностям другой feature. Если features должны взаимодействовать, используй явный контракт или общий domain/core-компонент, но не создавай циклические зависимости.

21. **Keep frameworks out of domain** — domain-слой импортирует только Foundation (и Combine для потоков состояния): без SwiftUI, UIKit, AVFoundation, MWDAT, Firebase.

22. **Reuse before abstraction** — прежде чем создавать новый `BaseViewModel`, `BaseRepository`, generic `UseCase`, `UiState` или другой общий abstraction, проверь, действительно ли уже существует несколько одинаковых случаев, которые требуют унификации.

23. **Navigation as a boundary** — не помещай бизнес-логику в navigation-код. Navigation должна связывать экраны, а не определять правила предметной области.

24. **Testing by responsibility** — тестируй бизнес-логику независимо от UIKit и SDK (XCTest, таргет QanatTests). Для domain используй unit-тесты; для ViewModel/presentation — соответствующие тесты состояния и поведения; для data — тесты Repository и интеграции с источниками данных там, где это действительно необходимо.

При конфликте принципов приоритет:

**KISS → YAGNI → существующая архитектура проекта → остальные принципы.**

Не усложняй iOS-проект ради формального соблюдения Clean Architecture или SOLID. Архитектура должна помогать разрабатывать и поддерживать приложение, а не создавать дополнительный код ради самой архитектуры.
